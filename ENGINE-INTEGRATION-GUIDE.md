# Quantum Learning Engine Integration Guide

This guide explains how backend and frontend developers can integrate the
quantum-learning engine into the main application.

The engine runs as an independent FastAPI service. It provides the Granite
3.2 8B Instruct tutor, learner-profile persistence, circuit validation,
Qiskit Aer simulation, Qiskit Composer export, and Jupyter notebook export.

## 1. Start the engine locally

```bash
cd Quantum-Algorithm-Learning-with-AI
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
ollama pull granite3.2:8b
uvicorn backend.app:app --host 0.0.0.0 --port 8000
```

The interactive API documentation is available at:

`http://localhost:8000/docs`

Configuration can be provided through `.env`:

```env
OLLAMA_URL=http://localhost:11434
OLLAMA_MODEL=granite3.2:8b
CORS_ORIGINS=http://localhost:3000,http://localhost:5173
```

The frontend should use the deployed engine URL in production, for example:

```env
VITE_QUANTUM_ENGINE_URL=https://engine.example.com
```

## 2.1 CodeChef-style exercises

Use `GET /exercises` to populate the exercise list. Load a complete exercise
with `GET /exercises/{id}`, then submit the learner's circuit:

```js
const result = await fetch(`${ENGINE_URL}/exercises/bell-state/submit`, {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({
    user_id: "student-123",
    circuit: {
      num_qubits: 2,
      shots: 1024,
      gates: [
        { name: "h", qubits: [0] },
        { name: "cx", qubits: [0, 1] }
      ]
    }
  })
}).then((response) => response.json());
```

The result contains `passed`, a percentage `score`, individual `checks`,
feedback, simulator counts, and probabilities. Public checks are deterministic;
hidden checks and curriculum-specific grading can be added later without
changing the submission shape.

## 3. Canonical circuit format

All clients should use this format when sending circuits:

```json
{
  "num_qubits": 2,
  "gates": [
    { "name": "h", "qubits": [0] },
    { "name": "cx", "qubits": [0, 1] }
  ]
}
```

Supported gates currently are:

| Gate | Qubits |
| --- | --- |
| `h` | One |
| `x` | One |
| `y` | One |
| `z` | One |
| `cx` | Two: control, target |
| `cy` | Two: control, target |
| `cz` | Two |
| `swap` | Two |
| `ch` | Two: control, target |
| `ccx` | Three: controls, target |
| `s`, `sdg`, `t`, `tdg` | One |
| `rx`, `ry`, `rz` | One, with one angle in `params` |
| `u` | One, with three angles in `params` |
| `measure` | One |

Qubit indexes are zero-based. The engine validates gate names, qubit ranges,
gate arity, and invalid CNOT control/target combinations before simulation.
Use `shots` on the circuit to select the number of measurement shots
(default `1024`, maximum `100000`). `POST /simulate` returns both measurement
counts and statevector-derived probabilities.

## 4. Frontend integration

### Tutor request

```js
const ENGINE_URL = import.meta.env.VITE_QUANTUM_ENGINE_URL;

export async function askTutor(userId, message, circuit) {
  const response = await fetch(`${ENGINE_URL}/tutor`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({
      user_id: userId,
      message,
      circuit
    })
  });

  if (!response.ok) {
    throw new Error(`Tutor request failed: ${response.status}`);
  }

  return response.json();
}
```

The response contains:

```json
{
  "answer": "Tutor explanation from Granite",
  "validated_errors": [],
  "learner_profile": {
    "user_id": "student-123",
    "preferences": {},
    "skills": {},
    "recent_errors": []
  }
}
```

Display `validated_errors` alongside the circuit. They are generated by the
deterministic validator and should not be replaced by an AI-generated error.

### Evaluate a circuit

```js
export async function evaluateCircuit(userId, circuit, source = null) {
  const response = await fetch(`${ENGINE_URL}/evaluate`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({
      user_id: userId,
      circuit,
      expected: {},
      source
    })
  });

  if (!response.ok) {
    throw new Error(`Evaluation request failed: ${response.status}`);
  }

  return response.json();
}
```

Successful evaluation returns:

```json
{
  "passed": true,
  "feedback": [
    "Circuit structure is valid. Run it in the simulator and compare the result with the exercise expectation."
  ],
  "simulation": {
    "engine": "qiskit-aer",
    "probabilities": {
      "00": 0.5,
      "01": 0.0,
      "10": 0.0,
      "11": 0.5
    }
  }
}
```

If Qiskit is not installed or available, the response reports
`"engine": "validation-only"` and does not claim to have simulated the
circuit.

### Load and save preferences

```js
export async function getLearner(userId) {
  const response = await fetch(`${ENGINE_URL}/users/${userId}`);
  if (!response.ok) throw new Error("Could not load learner profile");
  return response.json();
}

export async function savePreferences(userId, preferences) {
  const response = await fetch(`${ENGINE_URL}/users/${userId}/preferences`, {
    method: "PUT",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ user_id: userId, preferences })
  });
  if (!response.ok) throw new Error("Could not save learner preferences");
  return response.json();
}
```

Example preferences:

```json
{
  "pace": "visual",
  "hint_style": "guided",
  "difficulty": "beginner",
  "explanation_length": "short"
}
```

The frontend should provide visible controls for these preferences rather than
silently inferring sensitive learner characteristics.

### Composer and Jupyter exports

Send a circuit to `POST /integrations/composer` to receive OpenQASM. The UI
can show the QASM in a copyable code panel or link it to the Composer workflow.

Send `{ "title": "...", "circuit": { ... } }` to
`POST /integrations/jupyter`. The response is a Jupyter Notebook JSON document;
the frontend can serialize it as a `.ipynb` download.

## 5. Backend integration

The main backend should normally proxy requests to the engine instead of
exposing Ollama or the engine directly to public users.

Recommended request flow:

```text
Browser
  -> Main application API
      -> Authenticates the user
      -> Authorizes the requested learner/circuit
      -> Calls Quantum Learning Engine
          -> Granite through Ollama
          -> Circuit validator
          -> Qiskit Aer
      -> Returns a stable application response
```

Example Python proxy:

```python
import os

import httpx

ENGINE_URL = os.environ["QUANTUM_ENGINE_URL"]


async def tutor(user_id: str, message: str, circuit: dict | None) -> dict:
    async with httpx.AsyncClient(timeout=60) as client:
        response = await client.post(
            f"{ENGINE_URL}/tutor",
            json={
                "user_id": user_id,
                "message": message,
                "circuit": circuit,
            },
        )
        response.raise_for_status()
        return response.json()
```

The main backend should:

- Map its authenticated account ID to the engine `user_id`.
- Validate that the requested user owns the circuit or attempt.
- Apply application-level rate limits and quotas.
- Translate engine errors into the application’s standard error format.
- Avoid logging prompts, source code, or learner data unnecessarily.
- Keep the engine URL, Ollama URL, and credentials in server-side secrets.
- Add request IDs when proxying so failures can be traced across services.

## 6. Error handling contract

Clients should handle these cases:

| Status | Meaning | Client behavior |
| --- | --- | --- |
| `200` | Request succeeded | Render returned data |
| `400` | Invalid request relationship, such as mismatched user IDs | Show a request validation error |
| `422` | Invalid circuit or export input | Render gate-level validation feedback |
| `503` | Granite service unavailable | Show retry/service-unavailable state; do not fabricate an answer |
| `5xx` | Engine failure | Show a generic failure and report the request ID if available |

## 7. Production boundary

Before production use, the team must add authentication, HTTPS, exact CORS
origins, production database storage, rate limiting, observability, backups,
and isolated execution for any future arbitrary-code runner. See
`REQUIREMENTS-BEFORE-LAUNCH.md` for the complete launch checklist.
